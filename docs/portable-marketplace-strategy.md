# Portable Marketplace Strategy

Date: 2026-06-01

## Decision

`cofoundy-marketplace` remains the shared entry point, but it must publish
runtime-specific install surfaces instead of forcing every harness through one
manifest shape.

- Claude Code: keep `.claude-plugin/marketplace.json` with per-plugin GitHub
  repo sources.
- Codex: keep `.agents/plugins/marketplace.json`, but plugin entries must point
  to local paths inside the materialized marketplace checkout.
- Antigravity: add a generated bundle surface after a concrete CLI test. Current
  public docs describe plugins as bundles containing skills, agents/rules, MCP
  config, and hooks, but do not establish the same marketplace manifest contract
  as Claude or Codex.

The source of truth for operational content remains each plugin repo:
`cofoundy-toolkit`, `cofoundy-business`, `cofoundy-docs`, `cofoundy-finance`,
`cofoundy-founders`, `cofoundy-meta`, `cofoundy-pms`, and
`cofoundy-orchestrator`.

## Codex Audit Result

Codex supports Git sources for the marketplace itself:

```bash
codex plugin marketplace add owner/repo --ref main
codex plugin marketplace add https://github.com/owner/repo --sparse plugins/foo
```

That does not mean Codex supports remote sources per plugin entry. A local test
marketplace with this entry listed no plugins:

```json
{
  "name": "cofoundy-toolkit",
  "source": {
    "source": "github",
    "repo": "cofoundy/cofoundy-toolkit"
  }
}
```

Changing only the plugin source back to a local path made Codex list the plugin:

```json
{
  "name": "cofoundy-toolkit",
  "source": {
    "source": "local",
    "path": "./plugins/cofoundy-toolkit"
  }
}
```

Conclusion: current Codex `0.135.0` accepts remote marketplace repositories, but
does not accept Claude-style remote per-plugin `source` entries in
`.agents/plugins/marketplace.json`.

## Portability Options

| Option | Works for Codex remote install? | Drift risk | Operational cost | Verdict |
|---|---:|---:|---:|---|
| Symlinks under `plugins/` | No for a clean remote clone unless the sibling workspace already exists | Low locally, high remotely | Low | Keep for local dev only |
| Git submodules under `plugins/` | Unproven; likely brittle unless Codex initializes submodules recursively | Medium | Medium | Do not make it the primary path yet |
| Generated snapshots under `plugins/` | Yes, because Codex sees local plugin paths inside the marketplace checkout | Medium unless generated | Medium | Recommended for Codex remote |
| Remote per-plugin source entries | No in current Codex test | Low | Low | Use only for Claude Code |

## Recommended Architecture

Use a generator with a small shared catalog, for example
`catalog/plugins.yaml` or `plugin.meta.json` files in each plugin repo, to emit:

```text
cofoundy-marketplace/
  .claude-plugin/marketplace.json       # remote GitHub repo entries
  .agents/plugins/marketplace.json      # local ./plugins/<name> entries
  plugins/<name>/                       # generated Codex package snapshots
```

For local development, `plugins/<name>` may remain symlinks to sibling repos.
For release, a script should replace or materialize those paths as generated
snapshots in a release branch or release artifact consumed by Codex.

The generated snapshot is a distribution artifact, not the authoring source.
Developers edit only the source plugin repos. CI or a release command packages
the exact pinned version into the marketplace surface.

## Version And Cache Policy

Use one semantic plugin version per source plugin. The version SSOT should be
machine-readable and shared by all runtime manifests. The current SSOT is each
source plugin's `plugin.meta.json`; runtime manifests are generated.

Release flow:

```text
edit plugin source
run scripts/update-plugin.sh <plugin-name>
commit source plugin and marketplace release changes
```

`scripts/update-plugin.sh` bumps `plugin.meta.json`, regenerates manifests,
checks drift, refreshes Claude Code via `sync-plugin.sh`, and refreshes Codex
via `codex plugin add <plugin>@cofoundy`.

Cachebusters must be generated by the release command or CI, not by hooks running
from installed runtime cache paths. A hook may block an invalid commit, but it
must execute from the source repo or CI, not from `~/.codex/plugins/cache` or
`~/.claude/plugins/cache`.

## AGENTS.md And CLAUDE.md Unification Standard

To prevent runtime drift while maintaining low maintenance overhead, the current
local compatibility layer exposes existing Claude-era instruction files to
Codex and Antigravity:

*   **`CLAUDE.md` remains the source file** in repos that already use Claude
    Code instructions.
*   **`AGENTS.md` is a filesystem symlink pointing to `CLAUDE.md`**
    (`AGENTS.md -> CLAUDE.md`). This lets Codex/Antigravity load the same rules
    without duplicating markdown.
*   A future repo-by-repo migration may invert the relationship, but that should
    be deliberate and generated, not a manual rename.

## Antigravity Plugin Specification

The Google Antigravity harness supports modular capability extension through filesystem-based plugins, custom skills, and lifecycle hooks.

### 1. Installation Scopes
*   **Workspace Level:** Placed under `.agents/plugins/<plugin-name>/` or `_agents/plugins/<plugin-name>/` at the workspace root. Loaded dynamically for specific workspaces.
*   **Global Level:** Placed under `~/.gemini/config/plugins/<plugin-name>/` for cross-workspace activation.

### 2. Plugin Directory Layout
Each plugin bundle must conform to the following directory structure:
```text
plugins/<plugin-name>/
├── plugin.json         # Required metadata and capability declaration
├── mcp_config.json     # Optional MCP server integration parameters
├── hooks.json          # Optional lifecycle automated hook declarations
├── skills/             # Folder containing custom skills
│   └── <skill-name>/
│       └── SKILL.md    # Standard Operating Procedure for the skill
└── rules/              # Contextual constraints and policies
    └── <rule-name>.md
```

### 3. Hooks Architecture (`hooks.json`)
Antigravity integrates hooks into the agentic loop to enable automated validation, safety policy gating, and prompt decoration. Hook definitions inside `hooks.json` are classified into three strict functional stages:

| Stage | Mode | Blocking | Description & Use Cases |
|---|---|---|---|
| **`Inspect`** | Read-Only | No (Asynchronous) | Logging, audit telemetry, prompt journaling, metrics gathering. |
| **`Decide`** | Read-Only | Yes (Synchronous) | Policy enforcement, security scanning, credential checking, access gating. |
| **`Transform`** | Read-Write | Yes (Synchronous) | Context augmentation, data sanitization, prompt optimization. |

Example `hooks.json` contract:
```json
{
  "hooks": [
    {
      "event": "PreToolUse",
      "stage": "Decide",
      "command": "bash ./hooks/scripts/enforce-version-bump.sh"
    },
    {
      "event": "SessionEnd",
      "stage": "Inspect",
      "command": "python ./hooks/scripts/generate-prompt-journal.py"
    }
  ]
}
```
